# 工作流活动任务与订单草稿复核修复设计简报

## 用户与操作场景

已认证交易台用户在右侧 Agent 输入研究或交易意图。用户可能重复提交，也可能在交易区已有一份仿真订单草稿并要求复核。

## 页面任务与主要对象

页面继续只跟踪服务端唯一活动 `WorkflowRun`。订单复核的主要对象是当前仿真 `OrderDraft` 的版本引用，不是输入框中的证券代码。

## 信息层级与工作区区域

不改变顶栏、左侧标签、右侧 Agent 或浮层布局。只扩展右侧 Agent 创建命令：存在当前草稿时附带 `draft_id` 与领域修订；服务端活动冲突时恢复并跟踪返回的现有 Run。

## 真实数据来源、频率、新鲜度与失败状态

- 工作流状态来自 `/api/workflows/*` 和 PostgreSQL `workflow_runs`。
- 草稿来自仿真执行服务，按 `draft_id`、领域修订和记录修订校验。
- 行情监控沿用工作流已固化市场快照的 `provider_time`，不按浏览器当前自然日猜测交易日。
- 缺少草稿、版本不匹配、已有活动 Run 或确定性服务失败均显示服务端错误，不生成替代结果。

## 主要操作与启用条件

新工作流仅在服务端确认当前用户没有 `queued/running/cancel_requested/cancelling` Run 时创建。订单草稿复核还要求当前草稿存在且版本匹配；最终订单提交仍只能由用户在交易区独立确认。

## 受影响路由与桌面宽度

仅 `/desk`。所有宽度沿用现有布局；本次不改变响应式结构。

## 视觉与交互论点

沿用现有纸面、墨色、朱红当前态、双线分栏和任务线程样式，不新增颜色、卡片或布局。变化仅体现在已有错误文本和当前 Run 恢复行为。
